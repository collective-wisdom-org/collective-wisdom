# collective-wisdom

Shared agent workflows, skills and scripts for a set of apps.

## What this is

An agent team that moves tickets (in Linear, GitHub Issues or Jira) from spec to merge. A Chief of Staff thread keeps tickets moving through the ship loop (kickoff, build, open PR, security review, merge) in child T3 Code threads. A project manager ranks the backlog, starts its next ready ticket and tidies the tracker. Reviews and the OWASP security pass happen before every merge, and the human approves only the spec and the merge. Who does what is in [agent-team/docs/agents/org-chart.md](agent-team/docs/agents/org-chart.md).

Nothing here is specific to one app. Each app keeps its own facts (ticket prefix, repo, test command, invariants) in `docs/agents/project.md`, and the skills and scripts read that file. That file is the only part of the team an app commits. The skills, agents, scripts and shared role docs come from one clone of this repo on the machine (see Install on a machine).

## Layout

`agent-team/` mirrors a consuming repo, so every path inside the skills, scripts and docs stays valid. An app does not copy any of it. The machine install links it into your home folder.

- `agent-team/.claude/skills/`: the team skills (chief-of-staff, project-manager, ship-loop, kickoff-feature, build-from-plan, open-pr, security-review, merge-pr, write-ticket) and the supporting ones (human-writing, owasp-security, agent-security, auditing-security)
- `agent-team/.claude/agents/`: the documenter, compacter, implementer, code-reviewer and security-reviewer subagents, each a pointer to its role doc
- `agent-team/.claude/mods/`: the `status-pane` Claude Code mod, a pane that shows the Chief of Staff status (see `agent-team/docs/agents/status-pane.md`)
- `agent-team/scripts/`: the team scripts, their tests, `gh.sh`, `wait-for-ci.sh` and `prices.json` (the price table `agent_usage.py` and the `agent-gantt` mod both read)
- `agent-team/docs/agents/`: shared role docs (including the documenter), read from `~/.collective-wisdom/docs/agents/`
- `agent-team/docs/superpowers/README.md`: the docs layout, closeout and release note rules (the index is generated by `~/.collective-wisdom/scripts/docs_index.py`)
- Release notes, all in one file: <https://github.com/collective-wisdom-org/collective-wisdom/blob/release-notes/RELEASE_NOTES.md>
- `agent-team/templates/`: starting points for an app's `docs/agents/project.md`, `AGENTS.md`, the `.gitignore` lines and the per-user `user.md`
- `mods/agent-gantt/` and `.claude-plugin/marketplace.json`: the agent pane, a Claude Code mod installed per machine, not per app (see Agent pane). The marketplace also lists `status-pane`, which sits in `agent-team/.claude/mods/status-pane/`
- `install.sh`: the machine install only. It links this clone into your home folder (see Install on a machine) and touches no app. It is never copied into an app, and a target path or an old app flag is refused
- `tag-release.sh`: tags `origin/main` with the next release number (`v0.1`, `v0.2`, ...). Like `install.sh` it stays here and is never copied into an app

## Running a Chief of Staff in this repo

This repo runs its own Chief of Staff the way an app does: from the machine install at `~/.collective-wisdom`. It has no links into `agent-team/`.

- Run `./install.sh` from the root checkout once (see Install on a machine). Then run the Chief of Staff from the root checkout on `main`, like in an app.
- Sessions here, worktrees included, run the root checkout's skills and scripts. A branch's change to a skill or script is live only after it merges and the root checkout fast-forwards.
- Tests run `agent-team/scripts` by path, so a branch's own scripts are tested.
- `docs/agents/project.md` is real and local to this repo (tracker `github`, prefix `CW`). It is never shipped; an app starts its own from `agent-team/templates/project.md`.
- Edit shared files under `agent-team/`.
- A permission a tool saves to `.claude/settings.json` is this repo's own file. Commit it only if everyone working here should get it; put personal permissions in `.claude/settings.local.json` (gitignored).

## Requirements

- T3 Code, for the Chief of Staff and child threads (the skills call its thread tools)
- A ticket tracker: Linear (the Linear MCP), GitHub Issues (no extra tool) or Jira (the Atlassian Rovo MCP). See Choosing a tracker
- GitHub CLI (`gh`), used through `~/.collective-wisdom/scripts/gh.sh`; see `agent-team/docs/agents/github-auth.md`
- Python 3 and `pytest` (for example `uvx pytest`) to run the script tests
- Superpowers skills used by the ship loop: `brainstorming`, `writing-plans`, `using-git-worktrees`, `executing-plans`, `subagent-driven-development` and `verification-before-completion`

What works on which harness and tracker: [docs/compatibility.md](docs/compatibility.md).

## Adopt in a repo

An app commits one file from the team: `docs/agents/project.md`. From an empty repo to a running Chief of Staff:

1. Install the prerequisites listed under Requirements: T3 Code; `gh` signed in (`gh auth login`, see `agent-team/docs/agents/github-auth.md`); Python 3 and `pytest`; the superpowers skills, installed globally.
2. Install the team on the machine once, if you have not: see Install on a machine.
3. In T3 Code, start a Chief of Staff thread from the app's root checkout on the merge target branch and say `set up this repo` (or `start the team`; in a repo with no `docs/agents/project.md` it does the same). The Chief of Staff asks a few questions one at a time, each with its guess in brackets: your GitHub login (only when you have more than one), the subscription figure (only the first time on a machine), the tracker, the issue prefix, the test command and any repo rules. It writes `docs/agents/project.md` and a `.agent-team/` line in `.gitignore` on an `agent-team-setup` branch in a temporary worktree, asks before it creates the branch and worktree, commits, pushes or opens the PR (the read-only checks run without asking). It offers to remove an old app's copied team files in the same PR, and it never pushes to the merge target.
4. Merge the setup PR on GitHub, pull the root checkout, and say `start the team`. These rows of `docs/agents/project.md` are set to their defaults, and you can change them later by saying `set up this repo` again or by editing the file:
   - `Merge target branch` (the remote's default branch): the branch every PR merges into. See Configure a consuming repo.
   - `Review mode` (`agents`): `ci` lets a review bot in CI replace the review agents. See Review mode.
   - `Require teammate approval` (`off`): when `on`, a merge also needs an approving GitHub review from someone other than the PR author.
   - `Publish release notes` (`off`): when `on`, each PR carries a release note and every merge publishes the notes to the `release-notes` branch.
   - `Approval risk tolerance` (`strict`): which approvals the team takes without asking you. See Approval risk tolerance.
   - `No Hands` (`off`), `No Hands ticket cap` (`10`) and `No Hands cost cap (USD)` (`200`): whether you may start a No Hands run and its limits. See No Hands.
   - `Review after conflict resolution` (`off`): whether a conflict resolution is reviewed again before it can merge.
5. Set branch protection or a ruleset on the merge target branch that requires the checks listed in `Required CI checks` in `project.md`.

An app that was installed the old way, with the team copied into it, follows Moving an app off the copied team first.

## Install on a machine

One clone of this repo runs the agent team in every repo on the machine. Clone it somewhere permanent (not a worktree, which can go away), then run the installer with no target path from the clone's root:

```
./install.sh --dry-run   # preview, writes nothing
./install.sh             # install
```

To update, check out a newer release in the clone (`git fetch origin && git checkout v0.N`, or `git pull` on `main`) and run `./install.sh` again. Every repo then runs the new checkout; there is no separate pin. The rerun only adds links for new skills and agents and drops links to ones a release removed. A run with nothing to do reports `0 change(s)`.

It writes only under your home folder and touches no app. It links:

- `~/.collective-wisdom` to the clone's `agent-team/` folder. Skills and role docs call scripts as `~/.collective-wisdom/scripts/<name>`.
- Each skill into `~/.claude/skills/`, `~/.agents/skills/` (Codex) and `~/.cursor/skills/`, and each subagent into `~/.claude/agents/`. One link per name, so your own skills stay.

It also adds the Chief of Staff Stop hook to `~/.claude/settings.json` and `~/.cursor/hooks.json` (other keys and hooks are kept), and writes a short instruction between `<!-- collective-wisdom:begin -->` and `<!-- collective-wisdom:end -->` in `~/.claude/CLAUDE.md` and `~/.codex/AGENTS.md`. It says the team runs only in a repo with `docs/agents/project.md`. A rerun replaces that block and leaves the rest of the file alone. For Cursor it writes the same text to its own file, `~/.cursor/rules/collective-wisdom.mdc`, with `alwaysApply: true`, and a rerun rewrites that whole file. If you pasted the text into Cursor Settings, Rules before, you can delete that copy.

The run ends with `installed collective-wisdom <sha> [<tag>] from <clone>` and, when something needs you, a `TODO:` list. What lands there:

- A real file or folder, or a link to somewhere else, where a skill or agent link should go. (At `~/.collective-wisdom` itself this is not a TODO: the installer refuses and exits before writing anything, so remove it and run again.) The installer never replaces it; move or remove yours and run again.
- A `~/.claude/settings.json` that is not valid JSON, or whose `hooks.Stop` is not a list, and the same for `~/.cursor/hooks.json` and its `hooks.stop`. It is left alone; add the hook by hand.
- A `~/.claude/CLAUDE.md` or `~/.codex/AGENTS.md` that cannot be read as text, or has only one of the two marker comments. It is left alone; fix the file.
- A `~/.cursor/rules/collective-wisdom.mdc` that is a folder or cannot be read as text. It is left alone; fix the path.

A `~/.claude/settings.json`, `~/.cursor/hooks.json`, `~/.claude/CLAUDE.md`, `~/.codex/AGENTS.md` or `~/.cursor/rules/collective-wisdom.mdc` that is itself a link (dotfiles) is written at its target, so the link stays.

Per-machine settings (the GitHub login for each repo, your Claude subscription figure) live in `~/.config/collective-wisdom/user.md`, not in a repo's `project.md`. See `agent-team/docs/agents/github-auth.md` § Account per repo.

The installer refuses a clone that is not its own git repo root, and a linked worktree. It does not take a path: any argument but `--dry-run` (a path, or an old flag such as `--update`) exits 2, points at the removal command below and writes nothing.

## Moving an app off the copied team

An app installed the old way carries copies of the skills, agents, mods, scripts and shared role docs, and a version pin, `docs/agents/installed-from.txt`. Once the machine install is in place, one command removes them. Run it in the app:

```sh
~/.collective-wisdom/scripts/remove_app_copies.py --dry-run   # preview, writes nothing
~/.collective-wisdom/scripts/remove_app_copies.py             # remove
```

It reads the pin, lists the files the team shipped at the pinned commit, and deletes the ones the app still has, then the folders left empty, then the pin, then the pin's own folder if it is then empty, then the `.agents/skills` link. It never touches `docs/agents/project.md`, `AGENTS.md`, `.claude/settings.json` or `.gitignore`, and files the app owns (its own skills and scripts) stay. With no pin it prints `nothing to remove` and exits 0.

These stop before any delete:

- Exit 1, with a `changed <path>` line for each file. A copy was edited by hand, and deleting it loses the edit. Move the edit into this repo first, or run again with `--force` to remove it anyway.
- Exit 2 with `run 'git fetch origin'`. The pinned commit is not in the machine clone. Fetch there and run again.
- Exit 2 when `installed-from.txt` is malformed. It must read `collective-wisdom <40-character SHA>`, optionally followed by a `v0.N` tag. Fix the file or delete it by hand.
- Exit 1 when run inside collective-wisdom itself. Run it in an app.

A delete or folder prune that fails stops the run with exit 1 and `Stopped: cannot remove <path>: <err>.`. The message says whether the pin is still there. A rerun is safe.

A listed file that the app reaches through a link out of the app, such as a symlinked parent folder, is skipped with a `skip <path>` line and left alone, so the command never writes outside the app. The same goes for the pin, the five roots and the `.agents/skills` link.

Files collective-wisdom dropped in releases before the app's pin are not in the pinned list, so delete any that remain by hand.

Then read the TODOs it prints. If `.claude/settings.json` still has the old Stop hook for `cos_rotation_check.py`, remove it by hand, since the machine install runs the hook now. Check that `docs/agents/project.md` exists; if not, say `set up this repo` as in Adopt in a repo. Commit the removal as a PR in the app.

## Configure a consuming repo

Edit `docs/agents/project.md` in the app and replace every `<placeholder>`. The scripts read the first backticked token in a Value cell, so at least the issue identifier prefix, the repo, the branch pattern and the test command need real values. Anything marked `TODO(...)` is read as unset, and agents will stop rather than guess. The optional `Merge target branch` row (default `main`) names the branch every PR merges into; the root checkout stays on it.

## Approval risk tolerance

The `Approval risk tolerance` row in `docs/agents/project.md` § Identity sets which approvals the team takes without asking you: `strict` (none), `balanced` (Low risk only) or `permissive` (Low and Medium). High risk always waits for your `approve N`. The default is `strict`, and a missing row, an unknown value or a failed read counts as `strict`, so existing apps keep asking. The setting counts only as committed on the merge target branch (the `Merge target branch` row of `project.md`, `main` when unset), read from `origin`. CI, both review PASS comments (in `ci` review mode, no unresolved CI review thread instead) and every other merge gate apply at every level, and a PR that touches the setting, any role doc under `docs/agents/`, any script, the root `install.sh` or `tag-release.sh`, any dot-directory or dot-file at any depth (`.claude`, `.github`, `.cursor`, `.mcp.json` and the like) or any `AGENTS.md` or `CLAUDE.md` file always waits for you, and so does a ticket the Chief of Staff filed from its own observation. Nothing edits an existing `project.md` for you, so add the row by hand to turn it on. Details: `agent-team/.claude/skills/chief-of-staff/approvals.md` § Auto-approval.

## No Hands

Set the `No Hands` row in `docs/agents/project.md` § Identity to `on` (it is `off` by default; a missing row, an unknown value or a bad cap reads as `off`), then say `no hands` in the Chief of Staff thread. The Chief of Staff approves specs and merges itself at any risk level and keeps starting tickets from Todo and the Backlog until the Backlog is empty, the ticket cap or the cost cap is reached, a ticket blocks, or you say `no hands off` (finish what is running) or `stop everything` (stop now). Every review, CI check and merge gate still runs. A change to the files that decide approvals, the mode, the reviews and CI, a migration or a `flag:` path still waits for your `approve N`. When the run ends it posts a summary, and it never starts again without your next `no hands`. Details: `agent-team/.claude/skills/chief-of-staff/no-hands.md`.

## Review mode

The `Review mode` row in `docs/agents/project.md` § Review is `agents` (the default; a missing row means `agents`) or `ci`. In `ci` mode a review bot that already runs in CI replaces the code review and security review agents: the child answers and resolves the bot's review threads, and the merge gate passes a PR with green checks and no unresolved bot thread. Set `CI review bot login` to the bot's GitHub login; `CI review skill` optionally names a globally installed skill to follow when replying. Any other `Review mode` value is an error, not `agents`. `~/.collective-wisdom/scripts/ci_review.py list <N>` shows the threads. Details: `agent-team/.claude/skills/open-pr/SKILL.md` § CI review mode.

## Choosing a tracker

The `Tracker` row in `docs/agents/project.md` § Identity picks where tickets live: `linear`, `github` or `jira`. A repo with no row uses `linear`, so existing apps keep working. A project file started from the template has the row.

- `linear`: the default. Needs the Linear MCP and the Linear rows in `project.md`.
- `github`: tickets are GitHub issues in the repo, driven through `~/.collective-wisdom/scripts/gh.sh`. States and priority are labels.
- `jira`: through the Atlassian Rovo MCP. Untested: nobody with Jira access has run it, so treat it as a starting point.

Skills describe each step as an operation ("set the ticket to In Review"), and one adapter doc per tracker in `agent-team/docs/agents/trackers/` says how to do it. Switching an existing app to another tracker is not automated: open tickets, `.agent-team/state.json` and the `agent` labels do not move. Switch only with the team stopped and the state file empty.

## Releases

```sh
./tag-release.sh            # tag origin/main with the next v0.N and push the tag
./tag-release.sh --dry-run  # print the tag it would make
```

Run it by hand after a batch of merges you want machines to take. Apps do not pin to a tag. A machine takes a release by checking it out in its clone and rerunning `./install.sh` (see Install on a machine). It reads the tags on `origin` (not local ones), takes `origin/main`, and makes an annotated tag with the next number (`v0.10` follows `v0.9`), or `v0.1` when there are none. It refuses when `origin/main` already carries a `v0.N` tag. It pushes only that tag and never touches a branch. No skill runs it.

## Agent pane

`mods/agent-gantt/` is a Claude Code mod that opens a pane beside the chat and draws this session's agents as a Gantt chart. Each row shows the agent's name, repo, start, end, tokens, cost and model, with a bar that covers only the time the agent was working (waiting for a subagent, a background command or you is a gap). There is one row per task (one per prompt you send, named after the prompt's first line; a ship-loop child shows its stage, `Spec`, `Build` or `Merge`, and a ticket helper, backlog ranking or hygiene child shows its role), a subagent sits under the task it was spawned in, and main's usage that no task carries gets an `outside a task` row. Running bars grow while you watch. It is per person, not per app: install it once per machine at the user scope and it works in every repo and worktree you open. `install.sh` does not install it.

At the prompt of a terminal session:

```
/plugin install agent-gantt --marketplace collective-wisdom-org/collective-wisdom
```

From a shell:

```sh
claude plugin install agent-gantt --marketplace collective-wisdom-org/collective-wisdom
```

In the desktop app, where `/plugin` does not run: click + next to the prompt box, then Plugins, Add marketplace with `collective-wisdom-org/collective-wisdom`, then Add plugin.

In a repo that has `docs/agents/project.md` or `.agent-team/state.json`, the mod also writes this session's rows to `.agent-team/gantt/` for the [local dashboard](#local-dashboard). The pane opens when the session first starts a subagent. `/agent-gantt` opens it by hand. Costs come from `~/.collective-wisdom/scripts/prices.json`, the machine install's copy of the table `scripts/agent_usage.py` reads, so the column works in an app and in this repo. The pane shows a dash for cost only when that file is missing. The mod's events don't say which cache lifetime a write used, so it prices a write on the main thread at the 1 hour rate and a subagent's write at the 5 minute rate, which is what the transcripts show.

The marketplace also lists `status-pane`, the Chief of Staff status pane. It installs the same way, with `claude plugin install status-pane --marketplace collective-wisdom-org/collective-wisdom`. The old copy in an app's `.claude/mods/status-pane/` is removed by the removal command.

Update with `claude plugin update agent-gantt` (or `status-pane`). A PR that changes a mod bumps `version` in its `.claude-plugin/plugin.json` (`mods/agent-gantt/` or `agent-team/.claude/mods/status-pane/`); tagged releases don't cover it. The mod has tests (`rows.test.ts`, `snapshot.test.ts`, `timeline.test.ts`): `node --test mods/agent-gantt/hooks/*.test.ts` (Node 24 or newer).

## Local dashboard

`start the team` also starts a local dashboard for the repo and opens it in the T3 browser pane. It shows badges at the top right that count the threads awaiting merge approval and build approval and the tickets in the build queue, the Chief of Staff status, the tickets in three bands (Needs you, In progress, Queued), by stage inside each band, with their children (each linked to its issue and PR; in a GitHub-issues repo each stage lists its tickets by the issue's last update, newest first, read from GitHub about once a minute, while queued stages keep their start order), and a waterfall of the agents' work on each ticket card: one row per task in start order across the ticket's sessions, on an axis of active time only (time waiting on approvals takes no width), with each task's time and cost, a total line, and an `Agents` count of tasks. Cards waiting on approval have a red (merge) or amber (build) edge. Each stage section collapses from its heading, and the page remembers which ones you closed in the browser. A ticket's chart sits collapsed inside its card or, in the Queued band, its row. Next to it, a collapsed `Details` section starts with a links line (issue, `Spec`, PR and thread), then the stage, risk and next line, then the session, task and subagent counts, tokens, cost (only when every row is priced) and the last update; it stays open across refreshes. Below that comes the text, shown as formatted markdown (a table shows as a monospace block; the page never passes raw HTML through, and only `http(s)` links are clickable). While a ticket waits for build approval or builds, it shows the spec's Goal, Builds, Leaves out, Non-goals, Out of scope, Calls I made and Touches sections (read from the spec's commit with local git). From merge approval on (`awaiting-merge`, `merge`, `merge-queued`) it shows the PR's summary, release note, unproven items, changed files and the latest code and security review verdicts (read from GitHub about once a minute). A `Spec` link sits next to the `PR` link on every card and row that has a valid spec path and commit in state. Below the cards, a Merged list shows the pull requests of merged tickets (those with a ticket id in the branch or title) as rows, newest merge first, 200 at most, ten to a page with Newer and Older buttons; it is read from GitHub about once a minute and keeps the last list if GitHub cannot be reached. Each row has a `Spec` link when the PR added exactly one spec named for its ticket, and a collapsed `Details` section with the PR text, read only for the page on screen. Each row also shows the agents' cost and tokens for that ticket, summed over the Gantt sessions in its worktree. The dashboard records them every 30 seconds while it runs in `.agent-team/spend.json`, so they outlast the Gantt snapshots; only PRs that merge while the dashboard runs get a figure, and older rows show none. A row with recorded sessions also has a collapsed Agents chart like a ticket card's, drawn from `.agent-team/gantt-history.json`, which the dashboard writes the same way; it keeps the newest 500 sessions, so the chart outlasts the snapshots and the worktree, and older rows show none. The page keeps updating on its own and listens on localhost only. After a merge the server restarts itself on the new code, and the page says so if the new code fails to load. The page follows the macOS light or dark setting, which the server reads, because the T3 browser does not pass it through. Each thread has a copy button for its link, because T3 does not open thread links from a browser. Paste the link into T3.

The page has two tabs, Ship loop and Chief of Staff, and remembers the one you picked in the browser. Ship loop is the page described above. The Chief of Staff tab shows a card for the Chief of Staff with a `running`, `idle` or `paused` badge, a thread copy button and the gantt of its current session, found through `chiefSessionId` or `chiefThreadId` in state. Below it, a Project manager list shows the Backlog ranking and hygiene threads, newest first, ten to a page, each with its state, thread copy button, last update and a collapsed gantt. Finished threads stay in the list; the dashboard keeps the newest 50 in `.agent-team/gantt-history.json`, apart from the 500 ticket sessions. The list fills only with the updated agent-gantt mod, which writes the thread id and the opening heading of each session's first task prompt into its snapshot, so it stays empty until the mod is updated on the machine and a new ranking or hygiene child runs. Both tabs keep updating while you look at one. A session in the root checkout never shows on the Ship loop tab, and a worktree session never shows on the Chief of Staff tab.

The dashboard also keeps backups of `.agent-team/spend.json`, `gantt-history.json` and `state.json`. Each start of the dashboard (`start the team`, `resume`, `take over`) and, once a day, a running dashboard copies them into a dated folder under `~/.agent-team-backups/<repo folder>-<hash>/`. A file that is missing, a link or not valid JSON is skipped, nothing is written when no file changed since the last copy, and the newest 14 copies are kept. To bring files back, stop the dashboard (kill the pid in `.agent-team/dashboard.json`) and run `node ~/.collective-wisdom/scripts/dashboard/backup.ts restore --root <root checkout>`. It fills only missing files from the newest good copy; `--force` also replaces files that exist, after saving them as a new copy. `node ~/.collective-wisdom/scripts/dashboard/backup.ts --root <root checkout>` takes a backup by hand, and `--dest <dir>` on either command uses another folder. The copies stay on the machine and do not survive a lost disk.

## Propose changes

Open a PR here, not in the app. The checklist is in [CONTRIBUTING.md](CONTRIBUTING.md). Run the script tests with `uvx pytest -q agent-team/scripts` (CI does the same, and also runs `node --test agent-team/scripts/dashboard/*.test.ts agent-team/scripts/dashboard/page/app.test.js mods/agent-gantt/hooks/*.test.ts`). CI runs on pull requests only, so `main` is tested only through its PRs. A merge can still leave `main` red when another PR merged first, and nothing today tells the team when that happens. After it merges, tag a release with `./tag-release.sh`. Every machine takes the change when its clone checks out the new release or `main` and reruns `./install.sh`; no app needs a PR. Prose follows the `human-writing` skill: plain sentences, no em dashes.

## Known couplings

- T3 Code thread tools are named directly in the Chief of Staff, project manager and ship-loop skills. Tracker tools are named only in the adapter docs under `agent-team/docs/agents/trackers/`.
- An old app's copied `scripts/agent-team-update.sh` calls `install.sh --update --from <tag> <app>`. `install.sh` refuses that with exit 2 and a message that names the removal command, so the old call fails loudly and does not write.
- Plans, specs and as-built notes follow the superpowers docs layout under `docs/superpowers/`.
- The security review skill names Claude Code's `security-reviewer` subagent. Other hosts give `security-review.md` to a general subagent.
- Role docs for app areas (backend, frontend and so on) are not shared; each app adds its own.
